# 分层记忆管理

## 三层结构（扩展为四层）

### 🔴 核心记忆（memory 工具，每轮注入）
- 上限 5 条，每条 ≤150 字
- 只存"不知道就会出错"的信息
- 条件：一周后仍有价值 + 影响每轮行为

**必须存的核心**：
- 用户身份/偏好
- 当前活跃的模型/平台
- 关键限制（白名单、无信用卡等）

**不该存的**：
- 具体服务地址/端口/密码 → 移到参考笔记
- 已完成的部署细节 → 移到参考笔记
- 定时任务 ID → 移到参考笔记

### 🟡 参考笔记（文件，按需读取）
- 路径：**`~/.hermes/memories/notes/`** 目录（`notes/` 是 `memories/` 的子目录）
- 按主题分文件，用 `read_file` 读取
- 不消耗每轮 token，只在需要时读
- 真实布局见下方"记忆文件位置与读取"章节

**文件组织（实测布局，2026-06-20 验证）**：
```
~/.hermes/memories/
├── MEMORY.md              # 核心约束（每轮注入）
├── USER.md                # 用户画像（每轮注入）
├── hai_chuang_ops.md      # 机器专属 ops
├── <scope>_ops.md       # 机器专属 ops
└── notes/                 # 详细实战笔记
    ├── user_prefs_detail.md
    ├── foreman_8d_formula_v2.md
    ├── hermes_session_lessons.md
    └── archive/           # 已归档的旧笔记
```

**触发读取的场景**：
- 用户问"我的 RSS 密码是什么" → `read_file ~/.hermes/notes/services.md`
- 需要查服务器 IP → `read_file ~/.hermes/notes/servers.md`
- 定时任务出问题 → `read_file ~/.hermes/notes/cron-jobs.md`

### 🔵 语义记忆（向量库，按需检索）
- 存储：**SQLite-vec**（轻量）或 **Qdrant**（生产）
- 容量：10K-100K 条向量
- 延迟：<50ms
- 用于语义搜索，不靠关键词匹配
- 写入：重要信息（importance ≥ 0.8）自动入库
- 检索：LLM 提问时语义搜索相关记忆

**实现**（2026-06-26）：
- 无 sentence-transformers 时用字符 bigram + Jaccard 相似度（零依赖）
- `vector_store.py`：384 维，余弦相似度，自动淘汰（LRU 公式）
- 实测：搜索 "用户偏好" → 命中 "用户偏好简洁的代码风格"（0.549）
- 实测：搜索 "部署" → 命中 "旧主机 密码保护不能清理"（0.335）

**实现要点**（2026-06-26 实测）：
- 无 sentence-transformers 时用字符 bigram + Jaccard 相似度（零依赖）
- 向量存储：`vector_store.py`，384 维，余弦相似度
- 关键 bug：`put()` 必须更新已有条目的 `model` 字段
- 淘汰策略：LRU（importance × 0.3 + recency × 0.4 + frequency × 0.3）

### 🟢 历史归档（session_search，按需召回）
- 所有已完成的对话、调试过程
- 用 `session_search("关键词")` 召回
- 适合"上次我们怎么解决的"这类问题

## 记忆文件位置与读取（2026-06-20 立，必读）

### 两个独立 git 仓库（必区分，2026-06-20 实测翻车）

| 仓库路径 | 内容 | 性质 |
|---|---|---|
| `/root/.hermes/` | **用户记忆库** + config + secrets + plugins + skills(用户装) | git 仓库,remote backup = `root@:/root/.hermes-remote.git`（海创 ） |
| `/opt/hermes-agent/` | **Hermes Agent 源码** + 内置 skills + .venv + 升级源 | 独立 git 仓库,upstream = `https://github.com/NousResearch/hermes-agent` |

**关键事实**：
- 用户问"读取记忆库"/"看看记忆"/"我的偏好存哪"时 → 真实路径 = `/root/.hermes/memories/`
- **不是** `/opt/hermes-agent/memories/`（这个目录不存在,`ls` 会报 No such file or directory）
- **不是** `~/.hermes/notes/`（这是旧路径或泛指,实际是 `~/.hermes/memories/notes/` 子目录）
- 这两个仓库完全独立,升级 `/opt/hermes-agent` **不会**自动备份 `/root/.hermes/memories/`,反之亦然

### 读取记忆的标准流程（任何"读记忆"任务前必走）

```bash
# 1. 确认当前 pwd（避免在错的仓库里查）
pwd  # 应该是 /root 或 /opt/hermes-agent

# 2. 看 memories 目录 + git 状态
cd /root/.hermes
ls -la memories/                       # 看有哪些 .md 文件
git status memories/                   # 看哪些有未提交修改
git log --oneline -3 memories/         # 看最近 3 次自动提交时间

# 3. 读核心文件
read_file(/root/.hermes/memories/MEMORY.md)   # 核心约束(注入层)
read_file(/root/.hermes/memories/USER.md)     # 用户画像(注入层)
```

**反模式（2026-06-20 实测翻车）**：
- ❌ `cd /opt/hermes-agent && find . -name 'MEMORY.md'` → 找不到 → 浪费时间 + 报错
- ❌ 直接 `read_file(/opt/hermes-agent/memories/MEMORY.md)` → 报 "File not found"
- ❌ 在 `/opt/hermes-agent` 跑 `git stash` 试图"备份 memory" → 错仓库,跟 user 记忆无关

### git 未提交修改是常态（不修复）

`git status memories/` 经常显示：
```
 M memories/MEMORY.md
 M memories/USER.md
 M memories/notes/user_prefs_detail.md
?? memories/notes/<新笔记>.md
 D memories/<old-file>.md
```

**这是日常状态**（每轮对话都可能加 entry / 改偏好 / 加 notes）,**不是 bug**。看到不要慌,**不要**自动 `git add -A && git commit`——除非用户明确说"提交"。

**自动提交机制**：从 git log 看有 `auto: 2026-06-XX 23:00` 这种 daily auto-commit（应是 cron 任务在 23:00 推一次）。**触发词确认**："同步"/"提交"/"commit" 才手动跑,否则别主动 commit。

### 记忆库容量查看

```bash
# 当前 usage
cd /root/.hermes/memories
wc -c MEMORY.md USER.md notes/*.md | tail -1
# 字符上限看 hermes config
hermes config get memory.memory_char_limit    # 默认 6000
hermes config get memory.user_char_limit      # 默认 5000
```

**容量策略**（跨系统提示注入的字符预算）：
- MEMORY.md: 核心约束 ≤ 4000 字符最佳
- USER.md: 用户画像 ≤ 4000 字符最佳
- 详情走 notes/ 子目录,按需 read

## 迁移流程

从旧的全量记忆迁移到分层：

1. 审查当前 memory 条目
2. 核心条目（≤5 条）保留在 memory 工具
3. 详细信息拆分写入 `~/.hermes/notes/` 对应文件
4. 从 memory 中删除已迁移的条目
5. 验证：需要信息时能通过 read_file 或 session_search 找到

### 实操经验（实测数据）

**memory 工具参数注意**：
- `replace`：用 `old_text`（不是 old_string/new_string）+ `content`（新内容）
- `remove`：用 `old_text`（不是 content）
- 记忆条目是**独立条目**，不能用 `§` 分隔符匹配多条
- 每次操作后检查返回的 `usage` 百分比

**压缩技巧**：
- 合并重叠条目：配置+定价+Token → 一条；白名单+Gateway+Bot → 一条
- 去掉备注性文字（"暂不实施""已找到入口"）
- 地址/ID 截短显示（C265A05FD4650874A0C1313B1EADDFD9 → C265A05FD）
- 用"详细信息见 ~/.hermes/notes/"一句话索引替代详情

**典型迁移结果**：
- 12 条 → 3 条，1,956 字符 → 386 字符，88% → 17%
- 每轮对话省 ~1,570 token

**USER PROFILE 也会膨胀**：系统提示中的用户画像和记忆是分开的两块，如果画像也很长可以单独精简。

## 记忆融合策略

当用户要求"融合记忆"或"整理记忆"时：

### 步骤
1. **审查当前状态**：检查核心记忆和用户画像的条目数、字符使用率
2. **识别重复**：找出跨 target 的重复信息（如服务器信息在 memory 和 user 都有）
3. **合并相似条目**：将描述同一主题的多条合并为一条
4. **精简冗长描述**：去掉解释性文字，只保留事实
5. **删除过时信息**：已变更的配置、已完成的任务
6. **先操作后汇报**：直接执行清理，完成后展示 before/after 对比

### 实操流程（用户画像清理示例）

```
1. memory(action='add', target='user', content='测试')  → 确认能写入
2. memory(action='remove', target='user', old_text='测试')  → 清理测试条目
3. memory(action='remove', target='user', old_text='重复条目摘要')  → 删除重复
4. memory(action='replace', target='user', old_text='旧摘要', content='精简版')  → 精简
5. 每步检查 usage 百分比
```

**实测清理结果**：1188/3000 (39%) → 426/3000 (14%)，节省 762 字符

### 字符上限建议
| 使用场景 | memory_char_limit | user_char_limit |
|---------|------------------|----------------|
| 保守（简单任务） | 3000 | 1500 |
| 中等（推荐） | 6000 | 3000 |
| 激进（复杂项目） | 8000 | 4000 |

**改限值命令**：
```bash
hermes config set memory.user_char_limit 3000
hermes config set memory.memory_char_limit 4000
```
改完立即生效，下次对话的 system prompt 注入量随之变化。代价是每轮多注几百 token，但换记忆不丢。

### 清理 vs 扩容：先问用户

**默认倾向：扩容而非删内容**。当 USER.md / MEMORY.md 接近上限时：
- ❌ 不要直接进入"哪些条目可以删"的清理模式
- ✅ 先看 占用率：
  - **< 70%**：不动
  - **70-100%**：提示用户"扩限还是瘦身"，给两个选项 + 利弊
  - **> 100%**：已经截断，必须立刻行动——但仍要先问

**为什么先扩容**：本用户（2026-06-13）的偏好是"宁可多花 token 也要记忆完整"，从对话里观察到的强烈倾向：把 USER.md 砍到 17% 后，他立刻要求扩到 3000/4000 限制（合计 7000 字节、82% 富余），把"操作风格总则"等关键条目删了又后悔重新加回"token 显示要真实"那条——证明**关键行为偏好宁可多花容量也不丢**。

## 用户用编号批量删除时的执行流程

当用户说"USER.md 1 2 3 6 7不要"或"MEMORY.md 1 2 3 4 6不要"这种**编号清单**时：

### 步骤
1. **列"要删 vs 留下"清单**（**一行 brief 描述**每条内容 + 标 ⚠️ 警告最关键的 1-2 条）
2. **反问一次**："确认要连第 X 条也一起删？是 / 否"
3. **用户说"删了"** → 立即执行，**不要再警告**（用户已决策）
4. **执行后报告**：字节数变化 + 占用率 + **简述已删的关键影响**（一两条就够，不要长篇大论）
5. **预判可逆性**：用户可能加回部分条目，准备好快速 patch

### 关键规则
- **别反复警告**：用户给编号就是已经想清楚，第二次警告 = 啰嗦
- **别自作主张保留**：用户说"1 2 3 6 7不要"就只保留 4 5 8，**不要"我觉得 3 也很重要留下来吧"**
- **简报优于长报告**：每条用 5-10 字描述，不写完整原内容
- **⚠️ 标记核心**：最关键的 1-2 条加 ⚠️ 提示用户重新确认——但**只问一次**

### 反例（2026-06-13 差点犯）
❌ "你要删的 1/2/3/6/7 我先列出来：1. 操作风格总则（包含别扩展任务、代称先反问、QQ 用按钮三条核心偏好）... 2. 命令审批...（300 字警告）... 真的要删吗？"
✅ "删前确认——要删 1/2/3/6/7，留 4/5/8。⚠️ 第 1 条含'别扩展任务'核心。确认？"

## 清理信号
- 使用率 > 70%：考虑清理或扩容
- 条目数 > 8：考虑合并
- 用户说"记忆太乱"：立即整理
- 用户说"压缩"：先列条目让用户**编号选择**保留哪些，再执行
- 用户说"整合"/"疏通架构"：走架构审计流程（见下节），**不是压缩**

## 记忆架构审计（疏通架构）— 跟压缩是不同的事

**核心区分**：
- **压缩** = 字节减少（"压一下"）
- **架构审计** = 文件结构清晰（"整合"/"疏通架构"/"梳理一下"）——字节可能不变甚至微增

**触发词**：`整合` `疏通架构` `整理` `梳理` `归类`

### 5 步流程（实测：旧主机 / 海创 / 旧机 三机器场景）

1. **列清单**：`ls ~/.hermes/memories/` + 每文件 `wc -c`，看完整结构
2. **逐文件评估**，标 4 类问题：
   - 🔴 **事实错误**（IP 错、端口错、凭据过期）—— 最优先
   - 🟡 **结构问题**（一段塞多主题、编号重复、缺标题层级）
   - 🟠 **错位**（机器专属信息塞进跨机器 MEMORY、过期元数据留着）
   - 🟢 **过期**（上传元数据、已废弃接口、已完成任务细节）
3. **列修复顺序**（按风险从高到低）：🔴 事实错误 → 🟠 删除过期 → 🟡 拆段/移位 → 🟢 跳过结构好的
4. **每步执行后报告**字节变化，别攒到最后
5. **保留"核心 3 件套"**：USER.md（用户偏好）+ MEMORY.md（跨机器） + 1~N 个按需读的 ops 文件

### 关键 pitfall（2026-06-13 实测翻车）

**❌ 看到 ops_guide.md / server_X.md 之类的文件，默认以为是当前机器的**
- 用户纠正："你不是 hermes 吗，部署在 旧主机 上面的"
- 实际：ops_guide.md 是海创（妙妙屋）的运维指南，跟本机（旧主机）无关
- **修复前必须 `hostname` 确认当前机器** → 跟文件"标注的机器"对比 → 不一致先问用户

### 跨机器 vs 机器专属的归档原则

| 信息类型 | 该去哪 | 理由 |
|---|---|---|
| 机器区分表（3 台机器对比） | MEMORY.md（每轮注入） | 跨机器通用 |
| 某台机器的端口/服务/凭据 | `<machine>_ops.md`（按需读） | 机器专属，污染 MEMORY 是浪费 |
| 用户偏好、行为规则 | USER.md（每轮注入） | 永远相关 |
| 上传/备份元数据 | **直接删** | 一次性事件，5 天后无价值 |

**判断方法**：信息回答"哪台机器"问题 → 机器专属文件；信息回答"是什么机器"问题 → MEMORY。

### 整合 vs 压缩：用户说不同词走不同路

| 用户原话 | 走哪条 | 默认动作 |
|---|---|---|
| "压一下" / "压缩" / "容量不够" | 压缩 | 编号列条目让用户选保留哪些 |
| "整合" / "疏通架构" / "整理" / "梳理" | 架构审计 | 列文件清单 → 评估 → 用户确认修复顺序 |
| "加一条" / "记住这个" | 增量添加 | 直接 `memory` 工具加，不动其他 |

**别把"整合"当"压缩"处理**——整合的目标是结构清晰，不是字节最小化。

## 技能与记忆的边界

- 记忆只存稳定事实与偏好；技能存流程、方法和可复用规则。
- 当用户要求“整理/融合/统一”时，先判断是记忆压缩还是技能补充。
- 如果新学习的是“怎么做”，优先补技能；如果是“什么是/偏好是什么”，优先写记忆。

## 输出约定

需要读取笔记时，先 `read_file` 再回答，不要凭记忆猜测具体数值（端口、密码、ID 等）。
